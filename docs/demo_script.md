# デモ進行台本: ColdFusion 生産管理システムのモダナイゼーション

対象: 製造業の情報システム部門および開発部門
所要: 20分から30分
題材: 本リポジトリ (SEIZO-MES / CFML + MySQL、7画面)

## 0. 前提の共有 (2分)

- 20年以上継ぎ足しで運用された ColdFusion の生産管理システム
- 保守要員が枯渇し、仕様書もテストもない
- 論点は「移行できるか」ではなく「移行後に同じ挙動だと証明できるか」

画面を先に見せる: `http://localhost:8888/index.cfm` からダッシュボード、製造指示一覧、品質検査を順に開く。

## 1. Ask Devin: 資産の把握 (5分)

プロンプト例:

> このリポジトリの画面構成とデータフローを整理して、業務ロジックがどのファイルに埋め込まれているか一覧にしてください。

> 不良率の算出方法が画面ごとに違う箇所を洗い出して、どちらが正しい定義か判断に必要な情報を教えてください。

見せどころ: ダッシュボード (指示数ベース) と日報 (完了数ベース) の不一致、検査の再検査判定が `inspection.cfm` にしかないことを Devin が指摘する。

## 2. Ask Devin: 仕様復元と移行計画 (5分)

プロンプト例:

> 7画面のユーザーストーリーと、移行後の同等性を確認するためのテストマトリクスを作成してください。

> ColdFusion から Angular とバックエンド API への移行計画を、画面単位の依存関係と工程順で提示してください。

見せどころ: 仕様書がない資産から、ユーザーストーリー、技術ドキュメント、テストケースが生成される。Coppel 事例でも同じ順序で進めている。

## 3. Devin セッション: 実移行 (10分)

プロンプト例:

> `app/inspection.cfm` の業務ルールを保持したまま、Angular のコンポーネントと REST API に移行してください。判定ロジックはサービス層に切り出し、境界値のテストを追加してください。

> 上記の手順を Playbook にして、残りの画面へ並列展開してください。

見せどころ:

- 画面単位でセッションを並列に走らせられる
- 出力は GitHub の PR なので、顧客チームは通常のレビューフローのまま受け入れ判定ができる
- 移行と同時にテストが増えるため、同等性の証拠が残る

## 4. まとめ (3分)

- 言語非依存: ColdFusion のような保守困難な資産でも、読み解いて仕様を復元できる
- ドキュメントがない資産ほど、解析と仕様復元の効果が大きい
- 1画面ずつの人力移行から、Playbook による並列実行へ

## 補足: 実演で使える「壊れている点」

| 論点 | 該当箇所 |
|---|---|
| SQL インジェクション | `app/orders.cfm` の検索条件、`app/inventory.cfm` の倉庫絞込 |
| 認証なし | `app/Application.cfc` の `onRequestStart` |
| 二重登録で数が合わなくなる | `app/progress.cfm` の完了数の加算処理 |
| 棚卸差異が追跡できない | `app/inventory.cfm` の在庫直接更新 |
| N+1 クエリ | `app/maintenance.cfm` の設備一覧 |
| 指標定義の不一致 | `app/index.cfm` と `app/report.cfm` の不良率 |
