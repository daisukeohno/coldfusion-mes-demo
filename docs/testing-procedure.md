# CFML → Angular + NestJS 移行時のテスト手順

`app/inspection.cfm` の移行 (PR #3) で確立し、残り 7 画面 (index / orders / order_detail / progress / inventory / maintenance / report) の並列移行でもそのまま適用した手順。
目的は「新実装が旧 CFML 画面と同じ業務結果を返すこと (等価性)」を、自動テストと旧新並列の実機比較の二段構えで示すこと。

## 0. 前提環境の起動

```bash
docker compose up -d db web                            # MySQL 8 + Lucee (旧 CFML 画面 http://localhost:8888/)
(cd api && MES_DB_HOST=127.0.0.1 npm run start:dev)    # NestJS  http://localhost:3000
(cd frontend && npm start)                             # Angular http://localhost:4200 (/api を :3000 へプロキシ)
```

- `MES_DB_HOST=127.0.0.1` が使えるのは `docker-compose.yml` の `db` に `ports: ["3306:3306"]` がある場合のみ。
- DB 初期化に 1 分ほどかかる。`docker exec <db> mysql -umesuser -pmespass mesdb -e "select count(*) from t_kensa;"` で完了を確認する。
- DB データは volume に永続化されるため、**件数の期待値は絶対値ではなくテスト開始時からの増減で判定する**。
- `npm run start:dev` は watch モードなので、API 停止時の挙動を試すときは子プロセスまで落とし、
  `curl -s -m 3 -o /dev/null -w "%{http_code}" localhost:3000/api/...` が `000` になることを確認する。

## 1. 仕様の抽出 (テスト設計の入力)

移行対象の `app/*.cfm` から、テストで固定すべき挙動を列挙する。

- 入力検証の条件とメッセージ文言 (例: `測定値は数値で入力してください。`)
- 判定・計算ロジックとその評価順序、境界が厳密不等号 (`LT` / `GT`) かどうか
- SQL の抽出条件・結合・並び順・集計単位、サーバ側日付 (`curdate()`) の使用
- 画面ブロック構成、行の色分けクラス、注記文言
- CFML 固有の暗黙型変換 (`isNumeric()`、文字列の数値比較、倍精度演算)

抽出結果はそのままテストケース表になる。

## 2. ユニットテスト (api)

判定・計算ロジックは HTTP・DB 非依存の純粋サービスに切り出し、Jest でテストする。DB はモックし、`db.insert` / `db.query` の呼び出し有無と**バインドされた実パラメータ**を検証する。

必ず入れるケース:

1. 仕様上の境界値すべて (下限/上限ちょうど、閾値ちょうど、±最小単位)
2. 浮動小数点誤差が出やすい値 (差がちょうど閾値になる組合せ、小数 4 桁以上)
3. 非数値・列長超過・型不正の入力で **DB 書き込みが発生しない** こと
4. 正常時に期待値 (正規化済みの十進文字列と判定結果) で書き込まれること
5. 一覧・集計 SQL がパラメータバインドで、条件・並び順が旧 SQL と一致すること

例 (品質検査、規格 219.900 / 220.100):

| 測定値 | 期待判定 |
|---|---|
| 219.899 | NG |
| 219.900 | OK |
| 220.090 | OK |
| 220.091 | 再検査 |
| 220.100 | 再検査 |
| 220.101 | NG |
| `abc` | 400 `測定値は数値で入力してください。` (INSERT なし) |

## 3. 静的検査・ビルド

```bash
(cd api && npm test && npm run lint && npm run build)
(cd frontend && npm run build)
```

すべて成功してから PR を作成する。

## 4. テスト計画の作成

実機テストの前に、画面ごとにテスト計画を markdown で書き出す (例: `test-plan-inspection-r2.md`)。記載内容:

- 対象リビジョン、起動 URL、テスト開始時の DB 件数
- 根拠コード (どのファイルのどの挙動を確認するか)
- テスト ID ごとの操作手順・期待値・合格条件
- 旧 CFML 画面との比較表 (既知差異があればその行に明記)

## 5. 旧新並列の実機比較 (E2E)

ブラウザで旧 CFML 画面と新 Angular 画面を**同じ DB に対して**並べて操作し、表示値・集計・エラー文言を突き合わせる。testing agent に委譲し、録画とスクリーンショットを証跡として残す。

観点:

1. **境界値**: 2 のテスト表と同じ入力を画面から投入し、判定・メッセージ・行色が一致するか
2. **一覧・集計**: 件数、並び順、絞込 (指示番号・判定・倉庫など)、KPI の値が旧画面と一致するか
3. **登録・更新**: 登録後のメッセージ文言、フォームの復帰状態、DB の増分が期待どおりか
4. **入力エラー**: 不正値でエラー文言が出て **DB 件数が変わらない** こと
5. **障害時挙動**: API / DB を停止した状態で、古いデータが残らず日本語のエラーが表示されること、復旧後に戻ること
6. **画面遷移とスタイル**: リンク先、`app/mes.css` 由来の色分け・レイアウトの移植漏れ

`annotate_recording` で `setup` / `test_start` / `assertion` を付け、合否が録画から追えるようにする。

実機テストのコツ:

- メッセージ行の有無でフォームの座標が数 px ずれる。クリック前にスクリーンショット/DOM で位置を再確認する。
- 日本語入力は欠落することがあるため、自由入力欄は ASCII (`E2E-TEST-DEFECT` 等) を使う。

## 6. 差異の扱い

一致しない項目が出たら、原因を特定して次のいずれかに分類し、**勝手に旧挙動へ寄せない / 勝手に変えない**。

- **新実装のバグ** → 修正して再テスト (例: 進捗バーの CSS 移植漏れ、DB 障害時の英語エラー)
- **意図した仕様どおりの差異** → PR 本文に「意図的に変えた点」として記載しユーザーへ確認
  (例: 品質検査 `220.090` は CFML が倍精度誤差で `再検査`、新実装は整数ミリ比較で `OK`)
- **旧実装の既知の問題** → 結果が変わるため今回は保持し、PR 本文の「要確認」に列挙
  (画面間でコピーされた納期遅れ判定、ダッシュボードと日報の不良率の分母違い、トランザクション/履歴のない直接 UPDATE など)

## 7. 証跡の残し方

- PR 本文: 保持したルール / 意図的に変えた点 / テストでカバーした境界値 / 要確認事項
- PR コメント: 旧新比較表、スクリーンショット、録画へのリンク
- ユニットテスト件数と lint / build の結果
